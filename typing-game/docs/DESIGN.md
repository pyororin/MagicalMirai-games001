# 設計書:マジカルタイピング(仮称)

マジカルミライ プログラミング・コンテスト応募作品の企画・設計ドキュメント。

- ジャンル:**楽曲同期の判定を持つリズムゲーム。その入力方式がタイピング**(単なるタイピングゲームではない、という位置づけを対外的にも明示する)
- コンセプト:「歌詞を、メロディに乗せて打つ」。ドット絵という表現手法で、課題曲の世界観を描く
- ターゲット:スマホ(タップ+スライド上下左右の5入力)を基準に、PC も同じ入力体系(Space+矢印キー)で遊べるようにする
  ※ 当初は「PC の物理キーボード=ローマ字入力がメイン」だったが、2026-08-30 に5入力へ一本化(§3.4)

> **関連文書**:過去の入賞作品・類似サービスの調査は [`MARKET_RESEARCH.md`](./MARKET_RESEARCH.md) を参照。
> 2023年入選作品『Typing Lyrics』という同ジャンルの先行作が存在するため、**差別化要素(文字単位のタイミング判定 / ローマ字表記の全受理 / 先行入力 / 練習モード / スマホ対応)を意識的に作り込むことが本企画の生命線**。

## 1. 前提:コンテストの制約と著作権課題の解決

### 1.1 TextAlive App API を採用する(最重要の設計判断)

ユーザー側課題として挙がっていた「楽曲の著作権」は、コンテスト公式の **TextAlive App API**(産総研)を使うことで解決するのが基本線。

- マジカルミライのプロコンは例年「TextAlive App API を用いた Web アプリ(リリックアプリ)」が応募条件であり、**コンテスト指定楽曲**が API 経由で合法的に利用できる
- API は楽曲再生と同期した **歌詞のタイミングデータ(フレーズ / 単語 / 文字単位の発声開始・終了時刻)** を提供する
  - これはタイピングゲームにとって決定的に重要。「メロディに合っていれば高得点」という判定を、自前の譜面制作なしで実現できる
- ビート情報・サビ検出・声量(Vocal Amplitude)・V/A(感情価)などの音楽地図データも取得でき、演出に使える

→ **YouTube / ニコニコ動画へのオーバーレイ案は不採用**とする。ブラウザ拡張前提になり配布・審査のハードルが高く、規約リスクもあり、そもそも公式 API で楽曲問題が解決するため。ただし将来の一般公開版の拡張アイデアとして企画書内に温存する。

※ 応募年度の要項(対象楽曲・API バージョン・提出形式)は毎年更新されるため、実装開始前に当該年度の公式要項を必ず確認すること。

### 1.2 成果物の形

- 静的ホスティング可能な SPA(GitHub Pages / Cloudflare Pages 等)
- サーバー必須にしない(審査員が URL を開くだけで遊べることが重要)

## 2. コア課題:日本語タイピングとリズムの整合

「1文字(かな)を打つのにローマ字で2〜3打鍵必要」問題への設計回答。

### 2.1 判定の単位を「打鍵」ではなく「かな確定」にする

- リズム判定(メロディに合っているか)は **かな1文字が確定した瞬間** に行う
  - 例:「か」= `k` `a` → `a` を打った時刻を TextAlive の文字発声時刻と比較
- 個々の打鍵は「正誤判定」のみ(ミスタイプはコンボ切れ/減点)、タイミング点はかな確定時のみ
- これにより「し = shi(3打鍵)」でも「か = ka(2打鍵)」でも、リズム上は等価に扱える

### 2.2 判定ウィンドウ設計

TextAlive から得た文字の発声開始時刻 `t` に対して:

| 判定 | ずれ | スコア倍率 | 演出 |
|---|---|---|---|
| JUST | ±100ms | ×2.0 | 虹色ドットスパーク |
| GREAT | ±250ms | ×1.5 | 大きめキラ |
| GOOD | ±450ms | ×1.0 | 小キラ |
| OK(遅れ打ち) | フレーズ終了まで | ×0.5 | 演出なし |
| TYPED(先行入力) | ウィンドウより早い確定(§2.5) | ×1.0(基礎点のみ) | 控えめな点灯 |
| MISS | 未入力のままフレーズ終了 | 0 | 文字が砕けるドット演出 |

- 歌の発声は等間隔でないため、判定ウィンドウは前後の文字間隔に応じて動的にクランプする(隣接文字と窓が重ならないように)
- 「打ち切れなくても曲は止まらない」:曲は常に流れ続け、未消化文字は MISS として流れる(リズムゲームとしての気持ちよさを優先)

### 2.3 ローマ字入力の柔軟性(タイピングゲームの定石を踏襲)

- 複数表記を全て受理:`shi/si`、`chi/ti`、`ji/zi`、`fu/hu`、`sha/sya` など
- 「ん」の `n`/`nn`/`xn` 文脈依存処理、「っ」の子音重ね、拗音の分解入力(`sha` = `si`+`lya` 等)も受理
- 実装は **ローマ字トライ(先読み分岐グラフ)** を事前構築し、現在位置から有効な次打鍵集合を常に持つ方式(典型的なタイピングゲームエンジンの構造)
- ~~歌詞のかな読みは TextAlive API が提供する読みデータを利用~~ → **誤り。TextAlive は読みを提供しない**。
  読みは kuromoji でビルド時に事前生成して同梱する(`prototype/tools/build-readings.mjs`、
  詳細は `ontology/textalive.yaml` の no-reading-data-for-kanji)

> **方針転換(2026-08-30)**:入力方式を**タップ+スライド上下左右の5種類に一本化**した(§3.4)。
> ローマ字トライは `demo.html` と `src/romaji.ts` に残すが、実機版(`textalive.html`)の
> 判定パスからは外れている。理由は §3.4 を参照。

### 2.4 密度制御(歌が速すぎて打てない問題)

- 楽曲の文字密度は箇所により打鍵限界を超えるため、**難易度モード**で「打たせる文字」を間引く
  - EASY:フレーズ先頭文字+ビート上の文字のみ(残りは自動で流れる歌詞として表示)
  - NORMAL:単語の先頭文字+主要文字
  - HARD:全文字
- 間引きロジックはビート情報と文字間隔から決定的に計算(§6 の AI 活用候補でもある)

### 2.5 打鍵可能性の担保:先行入力・練習モード・速度調整

前提認識:**本来のピッチスピードで歌詞をリアルタイムに全打鍵し続けるのはまず不可能**。§2.4 の密度制御だけでは吸収しきれないため、以下を重ねて「無理ゲー」を回避する。優先度順に:

1. **先行入力(タイプアヘッド)— 最重要仕様**
   - フレーズが画面に表示された時点で、**発声を待たずにそのフレーズ全体を先行して打てる**(タイピングゲーム/音ゲーの定石)
   - 先行して確定したかなは「入力済みバッファ」に積まれ、発声時刻が来た瞬間に自動消化される
   - スコア設計との両立:
     - 発声時刻の判定ウィンドウ内で確定 → §2.2 のタイミング倍率(JUST〜GOOD)
     - ウィンドウより早い先行確定 → 「TYPED」扱いで基礎点のみ(倍率 ×1.0、コンボは継続)
   - これにより「速い箇所は先に打ち貯めて曲に置いていかれない」「乗れる箇所はリズムに合わせて JUST を狙う」という2層の遊びになる。上級者ほど先行に頼らずリズムで取りに行く、というスコアアタックの深みが生まれる
   - 先行できる範囲は「現在フレーズ+次フレーズ」まで(無制限にすると曲を無視した写経になるため)

2. **練習モード(事前に歌詞を打つモード)**
   - **リハーサルモード**:楽曲再生なし(またはフレーズ頭出しループ)で、同じ歌詞・同じ間引き譜面を自分のペースで打てる。フレーズ単位でリトライ可能
   - 本番モードとエンジンを完全共有し、時間制約だけを外す(`Timeline` を実時間ではなく「打鍵駆動」で進める実装)
   - リハーサル完了フレーズには本番の曲選択画面でマークを付け、「予習→本番」の導線を作る(ボカロ黎明期の「歌ってみた練習」文化とも文脈が合う)
   - プレイデータから苦手フレーズを抽出して重点練習に出す(§5 の事後分析と接続)

3. **再生速度の調整(スローモード)** — **検証済み・実装済み(2026-08-31)**
   - piapro 楽曲は `<audio>` として再生されるため `playbackRate` がそのまま効く。0.6× で
     `player.timer.position` が `audio.currentTime` に追従することを実測(5秒で誤差 -19ms)。
     音程は `preservesPitch` で保つ。0.50〜1.00× のスライダーとして実装し、等速でないプレイは
     リザルトに「練習プレイ」と明記する。iframe 再生になる楽曲ではスライダーを無効化する
   - 0.5×〜0.85× 程度の減速再生を練習用に検討。ただし **配信元によっては変更できない**
   - 減速するとピッチ・音質が犠牲になるため、位置づけは「練習モードのオプション」。本番スコアは等速のみ有効(ランキング的な公平性のため)
   - API 側で減速不可だった場合の代替:リハーサルモードのフレーズ頭出しループ+メトロノーム(ビート情報からクリック音を合成)で代用し、スローは諦める

**設計上の整理**:本番の「曲は止まらない・等速」という気持ちよさは崩さず、(1) 密度制御で要求打鍵数を現実的にし、(2) 先行入力で瞬間密度の山を均し、(3) 練習モードで習熟の場を別に用意する、という3段構え。速度変更は練習の補助輪であり、コア体験には含めない。

## 3. ゲームデザイン

### 3.1 画面構成(プレイ画面)

```
+----------------------------------------------+
|  SCORE 001230   COMBO x12        [♪ 進行バー] |
|                                              |
|         (背景:ドット絵ステージ、             |
|          ビートで明滅・サビで演出強化)         |
|                                              |
|   現在フレーズ(大):か が や く せ か い       |
|                     ^^ 現在文字ハイライト      |
|   ローマ字ガイド(小):ka ga ya ku ...          |
|   次フレーズ(薄表示)                          |
|                                              |
|  [ドット絵ミク:コンボで踊りが激しくなる]        |
+----------------------------------------------+
```

**2026-08-31 更新(設計やり直し)**:「歌詞かなを横に流し、現在ターゲットを中央に固定する」方式は破棄した。
理由は、その方式が **位置=順番** であり画面に時間軸が無いため、いつ打つかが見えず「出てきたものを反射で打つ」体験に
なっていたこと。加えて「かなを読む→母音を判定→方向に変換」という変換を毎回頭で行う必要があり、
5択の選択反応(約0.4〜0.5秒)を挟むと実データのかな間隔(中央値330ms)に原理的に間に合わない。

そこで **横位置=入力方向 / 縦位置=時間** の2軸に割り当て直した(実装: `prototype/textalive.html` build 10)。

```
+----------------------------------------------+
|  SCORE / COMBO            [進行バー] [一時停止] |
| -- 歌詞レーン(カラオケ) -- 背景に MV を敷く枠 --|
|      現在フレーズ(原文のまま・発声位置で着色)     |
|      次フレーズ(薄)                            |
| -- 5レーン落下フィールド --------------------- |
|    ←    ↑    ●    →    ↓                     |
|              [な]                             |
|    [い]            [た]                       |
|  ────────── 判定ライン ──────────  [はちゅね]  |
+----------------------------------------------+
```

- **横位置がそのまま入力方向**(左から ← ↑ ● → ↓)。かなを読まなくてもジェスチャが分かるので、
  上記の変換コストが消える。ノーツにはかなと方向記号を載せ、色は補助(色覚多様性のため記号も併記)
- **縦位置が時間**。ノーツは一定速度で判定ラインへ落ちる。既定の先読みは **2.0秒**
  (ハイスピード相当のスライダーで 1.2〜3.0秒)。単純反応 約0.25秒 + 5択の選択反応 約0.4〜0.5秒 +
  次ノーツの準備、から最低 1.2 秒は要ると見積もった
- 入力は従来どおり**画面のどこでもフリック**。レーンを狙って触る必要はない(片手・親指で完結させる)
- フレーズの開始位置をフィールドに破線で描き、次のフレーズがいつ来るかも先に見えるようにする
- 判定枠(late 600ms)を過ぎたノーツは MISS で流れる。フレーズ境界での「取り残し」は
  時間軸で自然に解決されるため、旧方式の強制送りロジックは不要になった
- プレイ中は**全画面**(`position:fixed` / `100dvh`)。落下距離を稼ぎ、ページスクロールと
  「フリックが効かない」問題を構造的に消す
- 広い画面ではプレイ面を中央に寄せて幅を制限する(レーンを画面幅いっぱいに広げると視線移動が増えるため)
- 右下にはちゅねミクのドット絵。OK / MISS で表情を変え、ボーカル音量に合わせて口パクさせる

### 3.1.1 アートディレクションの実装(build 11)

「よくある音ゲーの画面」に見えないことを要件として、ネオン+角丸+グローの語彙を捨てた。
5レーン落下という**遊びの骨格は音ゲーの経験がそのまま活きる形**を保ちつつ、
見た目は **ドット絵のライブステージ**に振り切っている。

- 画面はすべて 3〜4px のドットグリッドに吸着させて描く(角丸・ぼかし・影のブラーを使わない)
- パレットは oklch の限定色。方向色は彩度を落とし、明度差でも区別できるようにした
- ノーツは「かなブロック + 吹き出しの尻尾」。歌詞=声であることを形で示す
- 判定ラインは**5つのスピーカー**。ヒットでも拍でも鳴る(音楽に反応する画面)
- 背景はステージ:天井のトラスと吊りライト、客席のペンライト、床のドットグリッド。
  `player.findBeat()` の位相で明滅し、床は拍ごとに1行が下へ走る
- `player.findChorus()` がサビを返す間は画面の色相(`--hue`)をゆっくり回す
- はちゅねミクはステージ上に立たせ、拍で跳ね、入力方向へ残像がなびき、
  ボーカル音量で口パクする(演出とキャラが譜面と同じ画面に同居する)
- 打ったかなは歌詞バーへ吸い上がる(打鍵と歌詞表示が視覚的につながる)

加えて、画面の流れも「据わり」を作る:

- **あそびかた(チュートリアル)**: 曲を使わない20秒のドリル。5方向を1回ずつ落とすだけだが、
  判定・演出・SE は本番と同じパイプラインを通る(時計だけ差し替えている)。
  楽曲の読み込みを待たずに始められるので、起動直後に手触りが分かる
- **アトラクト**: 待機中もステージが動き、デモのノーツが5方向を順に落ちる。
  審査員が起動して最初の数秒で、遊び方と世界観が同時に伝わることを狙う(§6 の導線)
- **カウントイン**: 曲頭は拍を数える。いきなり始まらない
- **フィーバー**: コンボ12以上で客席のペンライトが総立ちになる
- **リザルト**: ランクのスタンプが押され、判定内訳が帯グラフになる
- **判定音**: レーンごとにヨナ抜き五音音階(ド・レ・ミ・ソ・ラ)を割り当て、
  打鍵そのものが旋律になるようにした。方向が音でも区別できる
- **ふりがな**: 事前生成した読みデータを使い、カラオケ行の漢字にルビを振る。
  「何を打つのか」が歌詞側だけでも分かる
- **キャラクターの2Dモデル化**: はちゅねミクを 32x40 の全身ドット絵にし、表情・口パク・
  腕のポーズを持たせた。拍で跳ね、入力方向へ残像がなびく。譜面と同じ画面に立たせることで、
  「演出」ではなく「一緒に演奏している相手」として置く
- **難易度ごとの先読み既定**: EASY 2.5 / NORMAL 2.0 / HARD 1.6 秒。HARD も最小間隔を
  125ms でクランプし、実測で最小48msだった無理な密度を落とした(理論値挑戦だが不可能ではない、へ)
- **サビの演出**: 色相回転に加え、トラスからディザのスポットライトが振れる。
  `prefers-reduced-motion` を尊重し、その場合は跳ね・揺れ・スポットライトを止める
- **共有**: リザルトから X の投稿画面を開くリンク(曲名・難易度・ランク・スコア)。
  押したときだけ開き、自動投稿はしない
- **判定ずれの調整**: -150〜+150ms のオフセット。直前のプレイの平均デルタを
  そのまま反映する「自動」ボタンを置き、キャリブレーションを1タップで済ませる

使用している比較的新しい CSS: `@property` + `oklch()` + `color-mix()`、container query、
`:has()`、`backdrop-filter`、`env(safe-area-inset-*)`、`ruby-position`。
いずれも GitHub Pages で完結し、サーバーは不要。

> 実装上の注意: `:root` に登録済みカスタムプロパティの `transition` を付けると、
> 以後その変数の更新が反映されなくなる(`ontology/infra.yaml` の
> registered-property-transition-freezes-updates)。色相の補間は JS 側で行っている。

### 3.2 スコアとフィードバック

- スコア = 基礎点 × タイミング倍率 × コンボ倍率
- コンボはミスタイプ or MISS で途切れる
- JUST を連続させると「フィーバー」:背景演出が一段派手に(サビ検出と重なると最大演出)
- リザルト:ランク(SS/S/A/B/C)、JUST 率、最大コンボ、打鍵速度(KPM)、リプレイ性を意識した1画面サマリ(スクショ共有想定、X 共有ボタン)

### 3.3 アートディレクション(ドット絵)

**方針転換の注記**:当初は「2010年前後のボカロ黎明期の再現」を固定テーマにしていたが、市場調査を踏まえて **「ドット絵という手法で、その年の課題曲を表現する」** に軸足を移す。理由は、コンテストの課題曲が毎年の楽曲コンテスト受賞曲(=新曲)であり、審査基準の第一項が「演出が**楽曲と同期して**魅力的に見えるか」であるため。曲の世界観を無視した固定テーマは減点要因になりうる。黎明期の空気感は「懐かしさの再現」ではなく「表現手法の選択」として残す。

- 16px〜32px 基準のピクセルアート、限定パレット、`image-rendering: pixelated`
- CRT 風スキャンライン、粗いディザ、8bit 風 UI フォント(かなは PixelMplus 等のフリーピクセルフォント)
- **楽曲への追従**:パレットとエフェクト強度を、TextAlive の V/A(感情価・覚醒度)とサビ検出に応じて動的に切り替える。曲ごとに「絵が変わる」ことを見せ場にする(過去入賞作にドット絵作品は見当たらず、手法自体の新規性は主張できる)
- 演出モチーフ:打ち終えた歌詞が画面を流れていく「コメント風テキスト」(既プレイの軌跡になる)
- キャラクターは初音ミク等の公式キャラ利用ガイドライン(ピアプロ・キャラクター・ライセンス)の範囲でドット絵化。コンテスト要項の二次創作規定に従う

### 3.4 入力方式(スマホ基準の5入力に統一)

当初は「PC=ローマ字 / スマホ=フリック」の二系統だったが、**タップ+スライド上下左右の5種類**に一本化した。
同一ロジック・別入力レイヤーという構造(`InputMethod`)は維持する。

- **5方向入力に一本化(2026-08-30 の決定)**:操作は**タップ / スライド上下左右の5種類だけ**。
  キーパッドは出さず、レーンのどこを触っても「現在ターゲットの行」の十字ガイドが出る方式にする
  - 方向は**かなの母音**で決まる:あ段=タップ、い段=←、う段=↑、え段=→、お段=↓
  - 濁点・半濁点・小文字(が/ぱ/っ/ぁ/ゃ)は**元の文字と同じ方向**。ナナメ入力は廃止(誤爆と学習コストが大きいため)
  - 「ん」=↑、「ー」=→
  - **小書き文字(っ・ぁ・ゃ)は打鍵対象にしない**。促音・拗音は発声が短く、独立した1操作にすると
    リズムが取れないため(歌詞表示には残し、直前のかなの一部として読ませる)
  - フリック確定=かな確定なので、**1かな=1操作**。ローマ字より音節とリズムの親和性が高く、「リズムに一番乗れるのはスマホ」という逆転の面白さを狙える
  - 判定は §2.2 と同一(かな確定時刻で判定)。確定は**指を離した瞬間**で、そこで SE を鳴らす
  - **指ごとに独立して受け付ける**(タッチ識別子で管理)。速い箇所は両手の親指を交互に置ける。
    1本ぶんしか見ないと、交互に置いた2本目が丸ごと無視される
  - PC も同じ入力体系に載せる(Space=タップ / 矢印キー=上下左右)。ローマ字入力は本流から外す
- **優先度を引き上げる**(市場調査による見直し)。理由は3点:
  1. 審査基準の「完成度」に「PC・タブレット・**スマートフォン**など意図した環境で正常に動作するか」が明記されている
  2. 入選後の**一般投票(公式アプリ「ミクナビ」経由)**があり、会場でスマホから触れることが票に直結しうる
  3. 先行作『Typing Lyrics』が **PC専用**であり、最も明確な差別化点になる。またスマホ対応のリズムゲーム TouchLyricWorld は優秀賞を獲っている
- **入口をスマホ専用として明示する**:PC ブラウザで開いたら QR コードでスマホへ誘導する分岐ページを出し、
  タッチ PC・動作確認向けに「このまま進む」リンクも常に用意する(`prototype/index.html`)。
  スマホと判定した場合はそのままゲームへ送る。QR 生成ライブラリは vendor に同梱し CDN 依存を作らない
- 実装順は PC キーボード → フリックだが、**応募版スコープに含める**。入力レイヤーの抽象化(`InputMethod` インターフェース)は最初から入れておく
- タップ簡易モード(表示されたかなをタップするだけ)は工数が逼迫した場合の保険として確保

### 3.5 ノーツの振り方: レーン式とリフレクト式(build 32 / 切替式)

ノーツの見せ方だけを差し替えられるようにした。**判定コア(かな→方向・判定窓・
密度制御・打ち逃し処理)は完全に共通**で、変わるのは「どこに湧いてどう動くか」だけ。
設定の「ノーツ」で切り替え、選択は localStorage に保存する。

| | レーン式(既定) | リフレクト式 |
| --- | --- | --- |
| 配置 | 5レーンを上から下へ落下 | 四方から中心の判定リングへ収束 |
| 判定点 | 画面下部の判定ライン | 中心の判定リング |
| 目線 | 5レーンを横に走査 | リング1点に固定 |
| ミク | 判定ラインの下(持ち手と反対側) | リングの内側(中央・背面) |

**方向の割り当て**: 来た方向へ打ち返す。い段(←)は左辺から飛んできて ← で左へ返す。
う段(↑)は上辺、え段(→)は右辺、お段(↓)は下辺。**湧く辺 = フリック方向**なので、
「かなを読まなくても打ち方が分かる」というレーン式の性質をそのまま引き継げる。

**あ段(タップ)**: 四辺からではなく、外から縮んでくる輪がリングに重なる瞬間にタップ。
矢印と形が根本的に違うので、四方から来るノーツと混ざらない。
「押し返す」ではなく「受け止める」動作として意味的にも分かれる。

**打ち返した後**: かなは来た方向へ飛び去り、画面の縁に客席のペンライトが1本増える。
拍に合わせて揺れ続けるので、コンボの積み上がりが数字ではなく景色で返る
(取りこぼすと1本消灯する)。

**読みやすさの担保**(360°を見張る負荷への対策):
- 軸は上下左右の4本だけ。斜めは使わない = 見る場所は4箇所
- 次に打つ方向は、リングの「その辺」の弧を光らせ、内側に方向記号を出す。
  中心はミクが立つので、そこに置くと読めない
- 縦長画面では軸ごとに距離が違うため、px 速度ではなく「残り時間の比率」で
  距離を決める(全軸が同時にリングへ到達する)

**縦位置(build 41)**: リング中心は画面高の 41%(以前は 53%)。
実機 390x844 では下端の左右隅から半径 250px ほどが親指と手のひらで隠れ、
右手・左手のどちらに持ち替えても下側は隠れる。build 40 の配置ではリング下辺(513px)と
下方向ノーツの湧き口(624px)がその中に入っていた。

| | build 40 | build 41 |
|---|---|---|
| 掲示板 | 曲名/スコア板 + 歌詞板の 2 枚(45〜210px) | 1 枚に統合(36〜150px) |
| 地平線(照明↔ステージ) | 270px | 168px |
| リング | 381〜513px(中心 447 = 53%) | 279〜411px(中心 345 = 41%) |
| 下方向ノーツの湧き口 | 624px | 522px |
| 客席(情報を置かない領域) | 画面下 26% | 画面下 38% |

助走距離(travel=111px)は横方向の制約で決まるため上へ寄せても変わらず、
速度・判定・先読みには影響しない。掲示板を 2 枚から 1 枚にしたのは、
筐体の枠だけで 30px 近く食って盤面が下がるため。

### 3.6 ミクの見た目と仕草(コンポーネント化 / build 40)

表情・腕のポーズ・間奏の仕草は `prototype/miku/miku.js` に切り出してある
(`window.MikuActor`)。アプリはキャンバスを渡し、口の開き具合と「いま歌っているか」を
毎フレーム伝えるだけで、表情の期限切れ・仕草の進行・間奏での自動仕草は
コンポーネント側が面倒を見る。**見た目を足すときは `EXPRS` / `POSES` / `GESTURES` に
1つ足すだけ**で済む(手順は `prototype/miku/README.md`)。

- 判定への反応: ヒット=にっこり+両手上げ、ミス=しょんぼり+うなだれ
- 間奏(歌詞が鳴っていない間)は 1.2〜3.8 秒おきにランダムな仕草
  (手を振る / ウインク / ピース / 手拍子 / 呼びかけ)。歌が始まるか判定が出ると中断する
- 拍の跳ねは**小節の頭だけ**(3拍子なら3回に1回)、振幅も従来の半分以下

## 4. 技術スタック

| レイヤ | 採用 | 理由 |
|---|---|---|
| 言語 | TypeScript | TextAlive App API が JS/TS 前提 |
| UI フレームワーク | React 18 + Vite | メニュー/リザルト等の宣言的 UI。希望スタックの React 系 |
| ゲーム描画 | Canvas 2D(必要なら PixiJS) | ドット絵は Canvas 2D + `image-rendering: pixelated` で十分。60fps はゲームループを React の外に置いて確保 |
| 状態管理 | Zustand(ゲーム進行)+ ゲームループ内は素のクラス | React の再レンダリングを打鍵判定パスに入れない |
| 歌詞・楽曲 | TextAlive App API | §1.1 |
| ホスティング | GitHub Pages / Cloudflare Pages | サーバーレス、審査しやすい |
| BE | **原則なし** | ランキング等を後日入れる場合のみ Go + SQLite/Turso か Cloudflare Workers を検討 |

- Go はフロント(WASM)で使う積極的理由がないため、応募版では見送り。BE を作る場合の第一候補として維持
- 打鍵イベントは `keydown` を `performance.now()` で記録し、TextAlive の再生位置 API と突き合わせる。描画フレームとは独立に判定(入力遅延を描画に律速させない)

### 4.1 モジュール構成

```
src/
  app/            # React シェル(タイトル、曲選択、設定、リザルト)
  game/
    loop.ts       # requestAnimationFrame ゲームループ(React 外)
    judge.ts      # タイミング判定(§2.2)
    romaji/       # ローマ字トライ、かな確定ステートマシン(§2.3)

```

`romaji/` と `judge.ts` は純粋関数+ステートマシンとして DOM 非依存で書き、ユニットテストを厚くする(この2つがゲームの品質そのもの)。

## 5. AI 活用の設計方針

リアルタイム判定パス(打鍵→判定→描画)に推論を挟むのは遅延的に不可。**AI は「事前生成」と「事後分析」に限定して使う**のが結論。

| 用途 | タイミング | 内容 | 実現性 |
|---|---|---|---|
| 譜面(間引き)生成の補助 | ビルド時/曲ロード時 | 文字密度・ビート・単語境界から「打たせて気持ちいい文字」を選定。ルールベースを基本とし、LLM で単語の意味的な山場(サビの決めワード)を残す重み付け | ◎ 本命 |
| リザルトの講評生成 | プレイ後 | JUST 率・ミス傾向(苦手な指/子音)から、ボカロ曲の世界観に寄せた一言講評を Claude API で生成 | ○ 演出として映える |
| 苦手分析→練習モード | プレイ後 | ミスした音節パターンを集計し、次回の EASY 間引きに反映(これ自体はルールベースで可) | ○ |
| 動的難易度(リアルタイム) | プレイ中 | ミスが続いたら次フレーズの間引き率を上げる。**ルールベースで実装**(AI 不要と判断) | ◎ ただし非AI |

- Claude API を使う箇所はネットワーク断でも劣化動作(定型文フォールバック)するよう設計
- API キーを露出させないため、講評生成を入れる場合のみ Cloudflare Workers の薄いプロキシを立てる(これが唯一の BE 候補)
- 応募版のスコープ判断:**講評生成1点に絞る**のが費用対効果最良。「AI がゲーム体験の中核」ではなく「世界観演出の仕上げ」と位置づける

## 6. リスクと対応

| リスク | 対応 |
|---|---|
| 年度要項の変更(対象曲・API 仕様) | 実装前に当該年度要項を確認。TextAlive ラッパを1モジュールに隔離し差し替え可能に |

| キーボードレイアウト差(JIS/US) | 打鍵は文字ベース(`event.key`)で処理、記号を歌詞対象から除外 |

| ブラウザの入力遅延・オーディオ遅延 | 設定画面にキャリブレーション(数拍打ってオフセット推定)を用意 |
| ピクセルフォントのライセンス | PixelMplus(M+ ライセンス)等、商用可・同梱可のものに限定 |
| **同ジャンルの先行入選作が存在**(2023年『Typing Lyrics』) | 差別化要素(文字単位タイミング判定 / 表記全受理 / 先行入力 / 練習モード / スマホ)を作り込み、作品説明では「タイピングゲーム」ではなく「入力方式がタイピングのリズムゲーム」として提示する。詳細は `MARKET_RESEARCH.md` |
| **競争激化**(応募 2023年39 → 2026年168作品) | 一次審査は審査員が全作品を試用する。**起動から30秒で楽しさが伝わる導線**(即プレイ可能、チュートリアル最小)を優先実装する |
| 課題曲と世界観のミスマッチ | §3.3 の方針転換(固定テーマではなく楽曲に追従するドット絵演出) |

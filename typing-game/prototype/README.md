# プロトタイプ — コアエンジン検証

設計書(`../docs/DESIGN.md`)のうち、最もリスクの高い判定コアを実装し、
成立性を検証したもの。TextAlive App API には依存しない。

## 中身

| ファイル | 内容 |
|---|---|
| `src/romaji.ts` | ローマ字入力エンジン。表記ゆれの同時受理、拗音/促音/撥音の文脈依存処理、確定遅延 |
| `src/judge.ts` | タイミング判定、先行入力、判定ウィンドウのクランプ、難易度別の密度制御 |
| `src/feasibility.ts` | 要求打鍵速度の見積もり |
| `demo.html` | 実際に遊べる検証機。Web Audio で音を合成し、オリジナル歌詞で判定を体験できる |

## 実行

```sh
npm install
npm test              # ユニットテスト 43件
npx tsx src/feasibility.ts   # 難易度別の要求打鍵速度を出力
```

`demo.html` はブラウザで直接開ける(ビルド不要)。

## 検証で分かったこと

1. **かな確定単位の判定は成立する。** 「し」を `shi`(3打鍵)で打っても `si`(2打鍵)で
   打っても、リズム上の単位は1つ。打鍵数の違いがタイミング判定に影響しない。

2. **確定遅延が必須。** 「ん」を `n` と打った時点では `n` で済ませるか `nn` と打つか
   判別できないため、確定を1打鍵保留して次の打鍵で分岐させる。ただし判定に使う確定時刻は
   保留を開始した打鍵の時刻を保持する(そうしないとリズム判定が遅れる)。

3. **等速の全文字打鍵は本当に不可能。** BPM 170 の16分音符連続では約 20 打鍵/秒が必要。
   密度制御(間引き)なしではゲームが成立しない。

4. **先行入力とタイミング判定の2層構造が機能する。** デモを自動打鍵で通すと
   TYPED 27 / MISS 0 / RANK B になる。つまり「先行入力だけで完走はできるが、
   高ランクにはリズムに乗せる必要がある」という意図した設計が成立している。

## 制約

この環境からは TextAlive App API・楽曲配信元(YouTube/niconico/piapro)の
いずれにも到達できないため、実楽曲との同期は未検証。歌詞タイミングは自前で生成している。
実データでの検証は、開発者トークンを取得した上でローカル環境で行う必要がある。

## textalive.html — 実楽曲接続版(フェーズ0スパイク)

TextAlive App API に接続し、マジカルミライ2025課題曲「ロンリーラン / 海風太陽」の
文字単位タイミングで同じ判定エンジンを回す検証機。曲URL入力で他の楽曲にも差し替え可能。

- 漢字・記号は打鍵対象外(かなのみ打つ)。**読みデータの取得は本実装の課題**として残る
- カタカナはひらがなに正規化して打鍵
- リザルトに平均デルタ(ms)を表示し、キャリブレーションの要否を判断できる
- アプリトークンは TextAlive の設計上クライアント埋め込みの公開値
- この作業環境からは TextAlive 系ホストに到達できないため、API をスタブ化した
  Playwright テストで統合コードを検証済み(実環境での音ズレ確認は手元ブラウザで)

# プロトタイプ — コアエンジン検証

設計書(`../docs/DESIGN.md`)のうち、最もリスクの高い判定コアを実装し、
成立性を検証したもの。TextAlive App API には依存しない。

## 中身

| ファイル | 内容 |
|---|---|
| `src/romaji.ts` | ローマ字入力エンジン。表記ゆれの同時受理、拗音/促音/撥音の文脈依存処理、確定遅延 |
| `src/judge.ts` | タイミング判定、先行入力、判定ウィンドウのクランプ、難易度別の密度制御 |
| `src/feasibility.ts` | 要求打鍵速度の見積もり |
| `index.html` | 入口。PC で開くと QR コードでスマホへ誘導し、スマホなら自動でゲームへ送る分岐ページ |
| `demo.html` | 実際に遊べる検証機。Web Audio で音を合成し、オリジナル歌詞で判定を体験できる(ローマ字入力) |
| `tools/build-readings.mjs` | 歌詞の読み(ふりがな)を kuromoji で事前生成するビルドスクリプト |
| `data/readings/*.json` | 生成済みの読みデータ(課題曲6曲)。歌詞全文の1文字に1読みが対応する |

## 実行

```sh
npm install
npm test              # ユニットテスト 43件
npx tsx src/feasibility.ts   # 難易度別の要求打鍵速度を出力
```

`demo.html` はブラウザで直接開ける(ビルド不要)。

## 検証で分かったこと

1. **かな確定単位の判定は成立する。** 「し」を `shi`(3打鍵)で打っても `si`(2打鍵)で
   打っても、リズム上の単位は1つ。打鍵数の違いがタイミング判定に影響しない。

2. **確定遅延が必須。** 「ん」を `n` と打った時点では `n` で済ませるか `nn` と打つか
   判別できないため、確定を1打鍵保留して次の打鍵で分岐させる。ただし判定に使う確定時刻は
   保留を開始した打鍵の時刻を保持する(そうしないとリズム判定が遅れる)。

3. **等速の全文字打鍵は本当に不可能。** BPM 170 の16分音符連続では約 20 打鍵/秒が必要。
   密度制御(間引き)なしではゲームが成立しない。

4. **先行入力とタイミング判定の2層構造が機能する。** デモを自動打鍵で通すと
   TYPED 27 / MISS 0 / RANK B になる。つまり「先行入力だけで完走はできるが、
   高ランクにはリズムに乗せる必要がある」という意図した設計が成立している。

## 制約

`demo.html` は TextAlive に依存せず、歌詞タイミングを自前で生成している(判定コアの検証用)。
実楽曲との同期検証は `textalive.html` 側で行う。

## index.html — 入口(スマホ誘導の分岐ページ)

本編は**スマートフォン専用**なので、`prototype/` を開いたときの入口を分岐ページにしている。

- スマホ(モバイル UA / iPadOS / 粗いポインタ＋狭い画面)と判定したら `textalive.html` へ自動遷移する
  - `?stay=1` を付けると自動遷移せず分岐ページに留まる(PC からの確認用)
- PC ではプレイ用 URL の **QR コード**(同梱の qrcode-generator で canvas に描画)と URL、コピーボタンを出す
- タッチ PC や動作確認のために「このまま PC で進む」リンクも常に出す(判定を外しても行き止まりにしない)
- `file://` や `localhost` で開いている場合は「その URL はスマホから開けない」旨を警告する

## textalive.html — 実楽曲接続版(build 15)

TextAlive App API に接続し、課題曲6曲の文字単位タイミングで判定エンジンを回すプレイ画面。
曲URL入力で他の楽曲にも差し替え可能(その場合は読みデータが無いのでかな表記のみが打鍵対象)。

### 入力(5種類だけ)

| 対象 | 入力 |
|---|---|
| あ段 | タップ |
| い段 / う段 / え段 / お段 | ← / ↑ / → / ↓ |
| 濁点・半濁点(が/ぱ 等) | 元の文字と同じ方向(が=か=タップ) |
| 「ん」 / 「ー」 | ↑ / → |
| 小書き文字(っ・ぁ・ゃ) | **打鍵対象外**(発声が短くリズムが取れないため) |

方向は「かなの母音」だけで決まる。**画面のどこでも**タップ/フリックでき、指を離した瞬間に確定+SE。
PC は Space=タップ、矢印キー=上下左右。

### 画面(5レーン落下)

**横位置=入力方向 / 縦位置=時間**。左から ← ↑ ● → ↓ のレーンにノーツが落ち、下部の判定ラインに
重なる瞬間に入力する。かなを読まなくても横位置でジェスチャが分かるのが要点(設計の経緯は
`../docs/DESIGN.md` §3.1)。

- 上段: 原文のカラオケ表示(発声位置で着色)。背面に MV レイヤーの枠を確保済み
- 中段: 5レーン落下フィールド(canvas)。**ドット絵のライブステージ**として描く
  (天井トラス・客席のペンライト・床のドットグリッド・判定ラインは5つのスピーカー)。
  `player.findBeat()` で拍に同期して明滅し、`player.findChorus()` のサビでは画面の色相が回り、
  トラスからディザのスポットライトが振れる
- ノーツは「かなブロック + 吹き出しの尻尾」。打つと、かなが歌詞バーへ吸い上がる
- はちゅねミクはステージ上に立ち、拍で跳ね、入力方向へ髪がなびき、ボーカル音量で口パク
- プレイ中は全画面表示になり、ページスクロールが無くなる
- `prefers-reduced-motion: reduce` のときは跳ね・揺れ・スポットライトを止める
  (CSS が効かない canvas 側も matchMedia で自前に見ている)

見た目の方針(なぜドット絵ステージなのか)は `../docs/DESIGN.md` §3.1.1 を参照。

### スライダー

| 項目 | 範囲 | 備考 |
|---|---|---|
| 先読み | 1.2〜3.0秒 | ノーツが見えてから判定ラインに届くまでの時間。ハイスピード相当。難易度を選ぶと既定値(EASY 2.5 / NORMAL 2.0 / HARD 1.6秒)に変わる |
| 速度 | 0.50〜1.00×(既定1.00) | `audio.playbackRate`。音程は保つ。等速でないとリザルトに練習プレイと明記 |
| 音量 | 0〜100(既定80) | |
| 判定ずれ | -150〜+150ms(既定0) | 端末の入力・音声遅延を吸収する。「自動」で直前のプレイの平均デルタを反映 |

いずれも localStorage に保存される。

### 画面の流れ

1. **アトラクト**: 待機中もステージが動き、デモのノーツが5方向を順に落ちてくる。
   押す前に遊び方が伝わる(ドット絵のロゴつき)
2. **カウントイン**: 曲頭、最初のノーツまでの拍を数える
3. **プレイ**: 全画面。コンボ12以上のフィーバーで客席が総立ちになる
4. **リザルト**: ランクのスタンプ、判定内訳の帯グラフと内訳表、X への共有リンク
   (押したときだけ開く。自動投稿はしない)

### 音

判定音はレーンごとのヨナ抜き五音音階(ド・レ・ミ・ソ・ラ)。打鍵そのものが旋律になり、
方向が音でも区別できる。SE はすべて Web Audio の合成音で、音源ファイルは持たない。

### その他

- **漢字は事前生成した読みデータでかなに開く**(下記)。読みが複数モーラの漢字は
  その文字の発声区間を等分してノート時刻にする。同じ読みデータを使って、
  カラオケ行の漢字には**ふりがな(ruby)**を振っている
- 判定枠(late 600ms)を過ぎたノーツは MISS で流れる(曲は止まらない)
- 裏タブに回ると rAF が止まって曲だけ進むため、非表示になったら一時停止する
- リザルトに平均デルタ(ms)を表示し、キャリブレーションの要否を判断できる
- アプリトークンは TextAlive の設計上クライアント埋め込みの公開値
- 検証用フックとして `window.DAKEN_DEBUG`(フレーズ/読み/Player)と `window.DAKEN_STATE`(譜面と判定状態)を公開している

### 読みデータの生成

```sh
npm install
node tools/build-readings.mjs          # 課題曲6曲
node tools/build-readings.mjs CyPO     # URL に該当する1曲だけ
```

カード JSON の `lyrics.url`(piapro の歌詞ページ)から本文を取り、kuromoji で読みを付け、
`data/readings/<songCode>.json` に「歌詞全文の1文字 = 1読み」で書き出す。
実行時は TextAlive の文字列をこの全文に突き合わせて読みを引く(ロンリーランで 386/386 一致)。
誤読は JSON の `readings` を直接手修正できる。

`data/readings/` を fetch するため、**file:// では動かない**。`python3 -m http.server` 等で配信すること。

取得まわりは GitHub Pages(サブディレクトリ配下)でも動くようにしてある:

- URL は相対パスではなく `new URL("data/readings/…", document.baseURI)` で組み立てる
- `?v=<ビルド番号>` を付けて古いキャッシュを掴まない
- `index.json` は Promise を共有して一度だけ読み、`onVideoReady` 側で待ち合わせる
  (先に曲が準備完了しても読みデータを取りこぼさない)
- 取得に失敗したら曲名の隣に「読みデータ取得失敗」と出し、URL と HTTP ステータスを
  ツールチップ・console・エラー画面の通信ログに残す(かな表記のみで続行)

## 実データ検証結果(2026-08-30、ロンリーラン / 海風太陽)

実 API から取得した全34フレーズ・文字単位タイミングでの分析:

| 項目 | 結果 | 設計への含意 |
|---|---|---|
| かな比率 | 表示386文字中284文字(74%)が打鍵可能なかな | かなのみでも1曲284ノーツで成立。残り26%(漢字等)の読み取得は本実装の課題 |
| かな間隔 | 最小51ms / 中央値330ms / 90%ile 1053ms | 最小51msは JUST 窓(±100ms)より狭い。**隣接ノートの窓クランプ(§2.2)は実データでも必須**(間隔<200msが 41/250 箇所) |
| EASY | 113ノーツ、要求 1.4〜2.0 打鍵/秒 | 初心者想定に合致 |
| (build 14 の実測) | EASY 219 / NORMAL 378 / HARD 423 ノーツ | HARD も最小間隔 125ms でクランプし、指が届く範囲に収めた |
| NORMAL | 164ノーツ、要求 2.1〜3.8 打鍵/秒 | 一般プレイヤー想定に合致 |
| HARD | 284ノーツ、中央値4.0 / 最悪8.3 打鍵/秒(最速フレーズ「ドアを開けることさえ怖かったあの朝」は9.6) | 「理論値挑戦」の位置づけ通り |
| 冒頭 | 最初のフレーズは15.4秒から | イントロ中にチュートリアル表示を出せる |

※ かな比率の行は「読みデータ導入前」の値。読みデータを入れた build 8 では
386表示文字すべてがかなに開かれ、**打鍵対象は284→450かな**になった。

→ **密度制御のパラメータ(EASY 2.0 / NORMAL 4.0 打鍵/秒)は実楽曲でもそのまま機能する**ことを確認。
onTimerReady(音源準備完了)まで実 API で到達済み。

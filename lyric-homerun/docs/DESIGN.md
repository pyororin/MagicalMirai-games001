## 0. ひとことで

**飛んでくる歌詞を、ミクがネギで歌に合わせて打ち返し、ライブ会場のスタンドいっぱいに届ける。**

- **打者 = ミク、バット = ネギ**(決定)。
- ボール = 歌詞のことば。まだ歌われていない「声になる前のことば」として飛んでくる。
- **打つ = 歌う**。ことばが歌われる瞬間にホームへ届き、ネギで捉えた瞬間に声になって飛んでいく。
- 投げるのは「曲」そのもの(提案: ステージのスピーカー。拍で鳴動し、拍に合わせて撃ち出す)。
- ホームラン = 歌詞がスタンドに飛び込み、落ちた場所の客席が光る。
  曲が終わると、**その回のプレイだけのスタンド(歌詞と光の景色)**が残る。

### 時間の3層(歌詞・音楽・タイミングの割り当て)
| 層 | TextAlive のデータ | ゲームでの役割 |
| --- | --- | --- |
| 拍 | `findBeat` / `getBeats` | **投げる側**。スピーカーの鳴動と発射、客席・照明の揺れ。「来るぞ」の予告 |
| 歌詞の発声 | 文字ごとの startTime/endTime | **打つ瞬間**。到達時刻=投げることばの発声開始。続く文字は打球の軌跡に、それぞれの発声時刻で現れる |
| 曲の構造 | 発声の長さ・ボーカル音量・サビ | **球種と盛り上がり**(§5)。間奏は投球なし(ミクが素振り・客席をあおる) |

- 飛んでくることばは輪郭だけ(未発声)。打つと色が付く(発声)。見逃すと輪郭のまま後ろへ抜ける。
  曲の音声自体は止めない・変えない(楽曲を改変しない)。
- 耳で聴こえる歌い出しと、ネギが当たる瞬間が一致する。**歌を知っているほど打てる**。

## 1. 原作から残すもの・変えるもの

| 原作の骨子 | 本作 | 理由 |
| --- | --- | --- |
| 1人の打者、操作は「位置」と「振る」だけ | **残す**。打者はミク。ポインタの横位置=ミクの立ち位置、押した瞬間にネギを振る | 単純操作が中毒性の核 |
| ホームランだけが得点 | **残す**。ヒットは歌詞が内野に落ちるだけ | 「届いた/届かない」が一目で分かる |
| N球中M本のノルマ(.300→.800) | **残す**。難易度ごとに同じ曲線を使う | 数字で設計された難度曲線 |
| 投手ごとに「読み」が変わる球種 | **残す**。ただし球種は**曲のデータから決まる** | 曲と無関係な変化にしない |
| 最終戦は全球種のランダム混合 | アンコール(最高難度)として残す | 到達目標 |
| 振りどきの手がかりが視覚だけ。消える球・蛇行は理不尽 | **変える**。全球が「歌われる瞬間」に届くので、**歌が手がかり**になる | 原作の「理不尽」を「音楽的」に置き換える。ここが原作を超える点 |
| 長押ししないと振り切れない | **変える**。押した瞬間に確定 | 入力の確定点を曖昧にしない(ontology: press-with-no-feedback) |
| ハチミツでの能力強化(周回前提) | **やめる**。曲中の「ボルテージ」に置き換え(§7) | 審査・投票は1〜2回のプレイ。周回しないと見えない要素は評価されない |
| 打球は消えるだけ | **変える**。打球が歌詞の演出になり、会場に残る | リリックアプリの本体 |
| ディズニーのキャラ・絵・音 | **一切使わない** | 権利。参考にするのは構造だけ |

## 2. 3つの要素をどう組み込むか

### リリックアプリ(歌詞がプレイで変わる)
- 歌詞は**常にどこかに出る**(掲示板 → ボール → 打球 → スタンド)。打てなくても歌詞は読める。
- **どう見えるかはプレイで決まる**: 当たりの良さで飛距離、振りの早い/遅いで方向、コースで高さが変わる(§8)。
- 終了時のスタンドは毎回違う。1枚絵として保存できる(canvas → PNG。サーバ不要)。

### 楽曲(曲のデータが遊びを決める)
- 投球の到達時刻 = 歌詞の発声開始時刻(TextAlive)。
- 投球の選び方 = 拍・フレーズ頭(§4)。球種 = 発声の長さ・ボーカル音量・サビ(§5)。
- 会場の照明・客席の揺れ = 拍(`findBeat`)と盛り上がり区間。
- どの曲でも譜面を自動生成する(課題曲は毎年変わる。曲ごとの手作り譜面は持たない)。

### 初音ミク
- **打者**。ネギを構え、プレイヤーの操作で振る。打つことが歌うことなので、ミクは歌い手のまま。
- 視点は原作と同じ打者の斜め後ろ(提案)。**ツインテールが振りに遅れてついてくる**のを一番の見せ場にする。
- 顔は会場の大型ビジョンに映す(提案)。ビジョンの中のミクは歌に合わせて口が動く(ontology: mouth-sync-source)。掲示板の歌詞と同じ場所なので視線が散らない。
- 入力から当たりまでを遅らせない: 押した瞬間にネギは当たりの位置にあり、振り切りの動きは後から付ける。

## 3. 画面と操作

想定環境: **スマホ縦持ち(主)** と **PC ブラウザ(マウス/キーボード)**。同じレイアウトを拡縮する(分岐しない。ontology: layout-fork-doubles-the-work)。

```
┌──────────────┐
│ 掲示板: いまのフレーズ   │ ← 投げられることばだけ球種の色
│   スタンド(歌詞が溜まる)  │
│      スピーカー(ステージ)    │
│          ●ことば            │ ← 奥から手前へ。近づくほど大きい
│  ミク(後ろ姿)─ホーム─(拍の輪) │ ← 画面高の約60%
│ ▓▓ 入力帯(見る物なし) ▓▓ │ ← 下35%。指で隠れてよい
└──────────────┘
```

- **ポインタ**: 入力帯で横位置=バット位置、**押した瞬間**にスイング(タッチは「振りたい場所をタップ」の1動作)。
- **キーボード**: ←/→ または A/D でコース、Space でスイング。
- 入力帯には情報を置かない(ontology: playfield-under-thumb)。
- 拍の手がかりをホームのすぐ横に無彩色で出す(ontology: beat-visible-only-on-the-character)。

## 4. 投球(譜面)の生成

候補は歌詞の各文字の発声開始。価値の高い順に、最小間隔を守って拾う(ontology: gap-only-thinning-kills-anticipation)。

- 価値: フレーズ頭 > 拍の上(±70ms) > 語頭 > その他
- **最小間隔は拍数ではなく実時間で決め、拍の整数倍に丸める**(曲の拍は 300〜513ms と幅があり、拍数固定だと曲ごとに密度が倍違う。拍子も 4 とは限らない。ontology: contest-songs-are-not-all-4-4)
- 同じ曲は毎回同じ譜面(乱数を使わない。覚えて上達できる。ホストのシークにも耐える)

実測(2025年課題曲6曲、`bunyutto-miku/app/data/songs` の固定データで試算):

| 難易度 | 拾う対象 | 最小間隔 | 球数(6曲) | 最短間隔 |
| --- | --- | --- | --- | --- |
| EASY | フレーズ頭だけ | 1.8秒 | 30〜49 | 1.8〜3.0秒 |
| NORMAL | +拍の上 | 1.2秒 | 59〜104 | 1.2〜1.5秒 |
| HARD | +語頭 | 0.8秒 | 84〜148 | 0.8〜1.0秒 |

EASY は原作(10〜50球)と同じ規模に収まる。HARD は多いので、上限(例: 100球)で価値の低い順に落とすかは試作で決める。

- 飛行時間 = 約0.9秒を拍に丸めた長さ(速度倍率1本で調整。ontology: speed-multiplier)。HARD では2球が同時に空中にありうる。
- 投げない歌詞は、ミクの口元から小さく流れて掲示板に残る。

## 5. 球種 — 曲のデータから決まる

到達時刻はすべて発声開始で固定。**変わるのは見え方だけ**で、歌を聴けば打てる。

| 球種 | 原作の対応 | 見え方 | 何から決まるか | 解禁 |
| --- | --- | --- | --- | --- |
| ストレート | イーヨー/ランピー | 等速 | 既定 | EASY |
| コース投げ分け | ピグレット | 内・中・外の3コース。投げる前にスピーカーの向きとホームの印で予告 | フレーズ内の順番(決定的) | NORMAL |
| ため球 | ラビット | ゆっくり→急加速 | 直前の文字が長く伸びた(ロングトーンの後) | NORMAL |
| ゆらぎ球 | カンガ/オウル | 蛇行。揺れ幅=その瞬間のボーカル音量。到達コースは印で予告 | ボーカル音量が大きい区間 | HARD |
| 消える球 | ティガー | 途中で消える。拍の輪と歌だけが頼り | サビ/盛り上がり区間 | HARD |
| 全部 | ロビン | 上の混合+高ノルマ | — | ENCORE |

- 掲示板の歌詞は、**実際に投げられることばだけ**球種の色で塗る(ontology: lyric-color-must-match-the-chart)。歌詞を読めば次の球が分かる。
- サビの検出は `findChorus` だけでは足りない。ボーカル音量の包絡で補う(ontology: find-chorus-is-sparse)。

## 6. 判定

スイング時刻 − 到達時刻 = ずれ。**タイミングが主、コースが従**(条件を同時に厳密に求めない。ontology: two-requirements-per-note)。

| ずれ(仮値) | 結果 | 歌詞の行き先 |
| --- | --- | --- |
| ±45ms | 特大ホームラン | スタンド最上段 |
| ±90ms | ホームラン | スタンド |
| ±150ms | ヒット(ノルマに数えない) | 内野に落ちる |
| それ以外 | 空振り | 小さく灰色でホーム後方へ |

- **早い→引っ張り(左)、遅い→流し(右)**。判定の文字を出さなくても、飛ぶ方向で早い/遅いが分かる。
- コースが1つ違うと1段階下がる(ホームラン→ヒット)。2つ違うと空振り。EASY はコースなし。
- 窓は隣の球との中間点で切る(ontology: char-interval-can-be-51ms)。
- 見逃しは到達+150msで確定(失敗の合図を遅らせない。ontology: miss-declared-too-late)。
- 球のない時の素振りは減点しない。振る音とネギの残像だけ返す。

## 7. ノルマ・難易度・ボルテージ

| 難易度 | ノルマ(ホームラン率) | 原作の対応 |
| --- | --- | --- |
| EASY | 30% | イーヨー(.300) |
| NORMAL | 50% | ラビット(.500) |
| HARD | 70% | ティガー(.700) |
| ENCORE(HARDクリアで解禁) | 80% | ロビン(.800) |

- 画面に「あと何本」を常時表示。達成した瞬間に会場演出が一段上がる(原作同様、以降は失敗してもクリア)。
- **ボルテージ**(強化要素の代わり): 連続ホームランで客席のペンライト(ネギ色)が増え、照明が派手になる。空振りで少し下がる。判定は変えない(腕前の表現であって、救済ではない)。
- 救済は設定の「アシスト」(窓を広げる)で明示的に選ぶ。結果画面にアシスト使用を表示する。

## 8. 歌詞演出(スタンド)

- ホームラン: ボールのことばが弧を描いて飛び、**続く文字がそれぞれの発声時刻に、軌跡の上へ1文字ずつ現れる**。着地点の客席が光り、ことばはそこに残る。
- 方向=早い/遅い、飛距離=精度、高さ=コース。**どこに歌詞を置くかはプレイヤーが決められる**(狙って打ち分ければ、スタンドに歌詞を並べられる)。
- ヒット/空振りでも歌詞は消えず、内野/ホーム後方に小さく残る。
- 曲の終わり: カメラを引いてスタンド全景。その回の歌詞の景色+成績。PNG 保存。
- 描画は「再生位置+スイング記録」からの純関数にする。シークされたら、その時刻より後の記録を捨てて描き直す(ontology: host-managed)。

## 9. ミク

- 斜め後ろからの全身(デフォルメ)。必要なポーズ: 構え(拍で揺れる) / スイング / 振り切り / 打球を見送る / 喜ぶ / 空振り。
- ツインテールは物理で揺らす(`miku-twintail` の知見を使う)。ネギは白い根元側を握り、緑の葉側で打つ。
- 大型ビジョン用の顔は `bunyutto-miku` の `miku-face.json` の方式を引き継ぐ。
- デザインはデータ(JSON)で持ち、コードは描くだけ(ontology: character-design-as-data)。
- **可愛いが絶対条件。口は極小の細い線。先に公式イラストを確認し、案をシートで提示してから本編に入れる**(CLAUDE.md の運用)。
- 投手を別のピアプロキャラクター(球種ごとにリン・レン等)にする拡張は、絵の量が増えるので本編完成後に判断する。

## 10. 音

- 効果音はコードで合成した自作音のみ(スイング、当たり、特大、着地、ノルマ達成)。
- 楽曲の一部と誤認されないよう、短い打撃音にする。音程のある長い音は使わない。重ねない(ontology: layered-sfx-feels-late)。
- バッファは事前生成し、最初のタップで AudioContext を起こす(ontology: oscillator-per-hit-latency / webaudio-se-silent-on-mobile)。

## 11. 技術構成

- 静的ファイルのみ。ビルドなしの ES Modules + Canvas 2D(ソースがそのまま読める。難読化なし)。TextAlive は `vendor/` に同梱(ontology: cdn-library-fragility)。
- 構成は `bunyutto-miku` に倣う: `app/`(公開物) / `test/`(`node --test`) / `docs/` / `tools/`。
- 純関数のコア(テスト対象): `chart.js`(投球生成) / `pitch.js`(球種と軌道) / `judge.js`(判定) / `flight.js`(打球と歌詞の配置) / `voltage.js`。
- 最初から入れるもの: ビルド番号の表示、通信失敗の URL とステータスの診断、`?demo=1`(固定データで動くデモ)、クレジット(産総研の研究成果に依拠・楽曲 URL・作詞作曲者名)と TextAlive App 利用規約へのリンク、応募作品である旨。
- Pages は `destination_dir: lyric-homerun` で配置(他企画を消さない)。

## 12. 審査基準との対応

| 基準 | 本作の答え |
| --- | --- |
| クリエイティビティ(曲と同期して魅力的か) | 全投球が発声時刻に届く。球種・照明・客席が曲のデータで動く。打球が歌詞のアニメーションになる |
| イノベーション(ユニークで未来の創作文化を予感させるか) | 「歌に応える」行為がそのまま歌詞演出を作る。観客が演出の一部になるライブの見立て。毎回違うスタンドが残る |
| 完成度(意図した環境で正常に動くか) | 静的・ビルドなし・単体テスト・デモモード・診断表示。スマホ縦とPCを同一レイアウトで |

## 13. リスクと未決事項

**判断をもらいたいもの**
1. **タイトル**(仮: とどけ!リリックホームラン)。原作を連想させる「〜のホームランダービー!」の形は避けた。
2. **強化要素(ハチミツ)をやめてボルテージに置き換える**方針でよいか。
3. **投げる側をスピーカーにする**、**視点は斜め後ろ+顔は大型ビジョン**の2点(提案)でよいか。
4. **AI と素材の線引き**: 規約は「コードの AI 支援は可、表示される絵・音・文章の AI 生成物は不可」。ミクのデザイン(JSON)や合成音の数値を AI が決めると、AI 生成物と見なされるおそれがある。**デザインは人が決める(または主催に確認する)**必要がある。これは既存企画にも当てはまる。
5. **募集期間中の Pages 公開**は「内容を推測させる行為」に当たりうる。本番の募集開始時に公開を止めるか決める。

**試作で確かめるもの**
- 判定窓の数値、飛行時間、HARD の球数上限。
- 消える球・ゆらぎ球が「理不尽」でなく「聴けば打てる」と感じられるか(原作を超える核。ここが駄目なら球種を作り直す)。
- 端末の音声遅延で当たりの音がずれないか(ontology: feedback-latency-budget。実測値を画面に出す)。
- スタンドに歌詞が溜まったとき読めるか(文字数は1曲 380〜760字・実測)。古いものを小さく薄くする等。
- 次回の課題曲が未公表。2025/2026年の課題曲で開発し、公表後に差し替える。

## 14. 進め方

1. **コア(画面なし)**: `chart.js` / `judge.js` を実データ6曲でテスト(球数・最短間隔が §4 の表に収まること)。
2. **打てる試作**: ストレートのみ、丸と文字だけの絵、`?demo=1`。判定窓と飛行時間を決める。← **ここで実機で触って方向性を確認**
3. **歌詞演出**: 打球→スタンド、結果の1枚絵。
4. **球種**: コース→ため球→ゆらぎ球→消える球の順。1つずつ「聴けば打てるか」を確認。
5. **ミク**: デザインシート提示 → 承認 → 本編。
6. **仕上げ**: ボルテージ演出、難易度、クレジット、診断、TextAlive ホスト対応、Pages。
